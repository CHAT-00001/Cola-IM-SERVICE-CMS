## 1. 本轮目标

在不改动其他业务模块、不重新设计 App 表、不立即抽象完整 Global 调度中心的前提下，完成当前 `cola_basic` 的最小可验证闭环：

```text
现有 App 表结构
    ↓
cola_basic App 数据模型
    ↓
port App
    ↓
repo_adapter App Adapter
    ↓
repository App Repository
    ↓
复制后的 FS 数据库结构
```

本轮重点是：

- ✅ 保留当前 App 表结构；
- ✅ 保留当前 `basic`、`cola_basic` 名称；
- ✅ 清理 `port / repo_adapter / repository` 中已经替换不完整的关键词；
- ✅ 让 App 的三层接口、类型、SQL 和表结构保持一致；
- ✅ 暂时复用复制后的 FS 数据库进行本地测试；
- ✅ 保留当前 Node 的临时实现，先验证数据链路；
- ✅ 为以后抽离 Global 模块保留扩展空间，但本轮不新增完整调度域。

---

## 2. 明确不做的事情

本轮禁止扩大改动范围：

- 不改 `cola_user`、`cola_video`、`cola_im` 等业务模块；
- 不改 `gate_http`、`gate_grpc` 现有网关链路；
- 不新建或改造 `module`、`region`、`service`、`deployment`、`instance`、`dispatch`、`registry`、`health` 等完整调度子模块；
- 不把 `basic` 改名为 `global`、`gate` 或其他名称；
- 不重设计当前 App 表；
- 不把 App 表拆成新的 App、Bucket、Binding 多表模型；
- 不迁移现有生产数据；
- 不立即把所有 FS 文件、媒体、上传代码移动回 `cola_fs`；
- 不通过全局关键词替换继续扩大迁移；
- 不实现完整 Kubernetes / Pod / 自动发布控制面。

未来的 Global 调度能力只在本文末尾作为后续方向记录，不作为本轮验收内容。

## 3. 当前约定

### 3.1 App 表

继续使用当前已经设计的 App 结构，不新增替代表。

当前 App 结构包含类似字段：

```text
id
_id
app_id
type_id
vendor_id
app_code
app_name
cdn_domain
bucket
access_key
secret_key
endpoint
region
config_json
remark
is_public
is_banned
status
is_deleted
created_at
updated_at
deleted_at
reviewed_at
```

本轮只做以下工作：

- 保持字段结构不变；
- 修正 Rust Entity、Info、Command、SQL 列表之间的字段映射；
- 统一 `app_name` 和数据库字段命名；
- 敏感字段不进入普通 AppInfo；
- 暂时允许 App 表承载当前的 Bucket / S3 配置；
- 后续再根据实际测试结果决定是否拆分存储绑定。

### 3.2 Node

`node` 继续使用当前借用 FS CDN 结构的临时实现，语义约定为后端部署节点：

```text
Singapore -> sg-01
Los Angeles -> la-01
```

本轮只保证：

- 当前 Node Entity 能够和当前临时表结构对应；
- 当前 Node Repository 的 SQL 表名、列名与 Entity 对齐；
- 不再扩展 Node 的部署调度能力；
- 不新增 Region、Service、Deployment、Instance 表；
- 后续再独立拆分 Node 表和 CDN 表。

注意：当前临时 Node 表结构可以先复用 FS 的 CDN 表，但必须在代码和计划中标记为临时方案。

### 3.3 FS 数据库

测试阶段复制现有 FS 数据库结构，优先验证当前代码是否可以正常连接和查询。

本轮数据库策略：

```text
先复制 FS 相关 Schema / Table
    ↓
按当前 Repository SQL 验证
    ↓
确认 App / Node / File / Media 查询链路
    ↓
再决定后续是否拆表、改 Schema 或增加迁移
```

不在本轮未经验证的情况下强行把所有 SQL 从 `cola_fs` 改为新的 Schema。

## 5. App 三层最小闭环

### 5.1 数据层

确认以下类型能够闭环：

```text
AppCreateCmd
AppEntity
AppInfo
```

建议关系：

```text
AppCreateCmd -> Repository::create -> AppEntity -> AppInfo
```

普通 Info 不返回：

```text
access_key
secret_key
```

如果当前业务内部确实需要 S3 配置，应使用内部专用结构，不直接复用对外 `AppInfo`。

### 5.2 Port 层

App Port 最小能力：

```text
create_app
get_app_by_id
get_app_by_app_id
list_apps
check_app
update_app / manage_app
single_delete
batch_delete（如果当前已有调用）
```

明确移除或延后：

```text
get_presigned_url
视频评论管理
文件上传
媒体处理
```

### 5.3 Adapter 层

Adapter 负责：

```text
参数校验
调用 AppRepo
Entity 转换
错误转换
日志记录
```

Adapter 不负责：

```text
直接生成 S3 URL
直接处理文件上传
混用 FS Bucket Port
```

### 5.4 Repository 层

Repository 负责：

```text
当前 App 表的 SQL 查询与写入
软删除
分页查询
app_id 唯一性检查
```

Repository 不负责：

```text
业务权限编排
API 响应包装
S3 Client 构建
```
