## 1. 需求目标

实现面向前端评论区的统一视频评论列表接口，支持普通评论列表、评论回复列表，以及从通知中心进入指定评论并高亮显示。

当前操作用户 `uid` 必须由可信会话注入，不允许由前端 `CommentGetCommand` 传入。`uid` 主要用于评论视图对象中的 `is_owner`、点赞状态等用户态展示判断。

////////

## 2. 请求场景

### 2.1 普通顶级评论列表

请求只携带视频 ID：

```json
{
  "video_id": 1001
}
```

处理规则：

- 查询指定视频的顶级评论；
- 默认不携带 `parent_id`；
- 默认不携带 `by_id`；
- 查询条件必须包含 `parent_id IS NULL`；
- 所有返回评论的 `is_highlight` 都为 `false`。

////////

### 2.2 查看评论内嵌回复

请求携带父评论 ID：

```json
{
  "video_id": 1001,
  "parent_id": 2001
}
```

处理规则：

- 查询 `video_id = 1001` 且 `parent_id = 2001` 的子评论；
- `parent_id` 为可选参数，默认不传；
- 只返回指定父评论下的回复列表，除非通知跳转场景需要补充父评论上下文；
- 返回的子评论默认 `is_highlight = false`。

////////

### 2.3 从通知中心进入被互动评论

请求携带目标评论 ID：

```json
{
  "video_id": 1001,
  "by_id": 3001
}
```

处理规则：

- `by_id` 为可选参数，默认不传；
- 查询结果中，`id == by_id` 的评论设置 `is_highlight = true`；
- 其他评论设置 `is_highlight = false`；
- `by_id` 必须校验属于当前 `video_id`，不能只根据客户端 ID 查询。

////////

### 2.4 目标评论是子评论

当 `by_id` 命中的评论存在 `parent_id` 时：

1. 查询目标子评论；
2. 根据目标子评论的 `parent_id` 查询父评论；
3. 返回父评论和目标子评论的上下文；
4. 目标子评论 `is_highlight = true`；
5. 父评论 `is_highlight = false`，除非 `by_id` 本身就是父评论 ID；
6. 其他评论 `is_highlight = false`。

推荐第一阶段返回扁平列表，依靠 `parent_id` 建立父子关系：

```json
{
  "comments": [
    {
      "id": 2001,
      "parent_id": null,
      "is_highlight": false
    },
    {
      "id": 3001,
      "parent_id": 2001,
      "is_highlight": true
    }
  ]
}
```

暂不引入递归嵌套 `replies` 字段，避免破坏现有 `CommentListResponse` 结构。

## 6. CASE 层业务编排

文件：

```text
D:\rust\short-video\cola_video\src\case\comment\get.rs
```

建议统一入口：

```rust
pub async fn case_get(
    uid: i64,
    cmd: CommentGetCommand,
    page: i64,
    qty: i64,
    offset: i64,
    ctx: AppContext,
) -> Result<CommentListResponse>
```

业务分支：

```text
by_id 有值
  ↓
查询目标评论
  ↓
目标评论是子评论？
  ├─ 否：查询目标评论所在的顶级列表，并标记目标评论
  └─ 是：查询父评论和目标子评论上下文，并标记目标子评论

by_id 无值、parent_id 有值
  ↓
查询指定父评论的回复列表

by_id 无值、parent_id 无值
  ↓
查询视频顶级评论列表
```

CASE 负责：

- 校验 `by_id` 属于当前视频；
- 校验 `parent_id` 属于当前视频；
- 编排目标评论和父评论的组合返回；
- 将命中评论 ID 传给 Assembler；
- 传递可信 `uid` 计算 `is_owner`；
- 计算正确的分页信息。

## 7. Port / Adapter / Service 改造

建议将获取接口拆分为以下能力：

```rust
get_top_comments_by_video(
    video_id,
    limit,
    offset,
)

get_replies_by_parent(
    video_id,
    parent_id,
    limit,
    offset,
)

get_comment_by_id(
    video_id,
    comment_id,
)

get_parent_comment(
    video_id,
    parent_id,
)
```

职责：

- Port：定义异步 trait 接口；
- Adapter：只负责调用 Service；
- Service：调用 Repository，并将 Entity 转换为 `VideoCommentInfo`；
- 不在 Service 中解析 HTTP 参数；
- 不在 Repository 中判断 `is_highlight`，高亮属于 VO 展示逻辑。

## 8. Repository / PostgreSQL 查询设计

### 8.1 顶级评论

查询条件：

```sql
WHERE video_id = $1
  AND parent_id IS NULL
  AND status = 1
ORDER BY add_time DESC
LIMIT $2 OFFSET $3
```

### 8.2 子评论

查询条件：

```sql
WHERE video_id = $1
  AND parent_id = $2
  AND status = 1
ORDER BY add_time ASC
LIMIT $3 OFFSET $4
```

### 8.3 目标评论

查询条件：

```sql
WHERE id = $1
  AND video_id = $2
  AND status = 1
```

### 8.4 父评论

查询条件：

```sql
WHERE id = $1
  AND video_id = $2
  AND parent_id IS NULL
  AND status = 1
```

所有查询都必须校验 `video_id`，不能只使用客户端提供的评论 ID。

## 11. 分页设计

统一使用：

```text
请求：page / qty
后端：limit / offset
```

要求：

- `page` 最小为 `1`；
- `qty` 限制在 `1..=50`；
- `offset = (page - 1) * qty`；
- 不再将返回页码固定为 `1`；
- `total` 应使用独立 `COUNT(*)` 查询；
- 不使用当前页 `infos.len()` 作为真实总数；
- `has_more` 根据真实 `total` 计算；
- 补充父评论时不得破坏分页语义，必要时在 CASE 层去重。

暂时无法增加 Count 查询时，`has_more` 可临时使用：

```rust
infos.len() == qty
```

但正式版本应补充真实总数查询。

## 12. 数据去重与安全校验

必须保证：

- `by_id` 对应评论属于 `video_id`；
- `parent_id` 对应父评论属于 `video_id`；
- 子评论的 `parent_id` 与目标视频一致；
- 父评论只返回一次；
- 目标评论只返回一次；
- SQL 查询全部使用绑定参数；
- 不信任客户端传入的 `uid` / `user_id`；
- 空 `parent_id` 表示顶级评论列表，不表示“查询所有层级评论”。
