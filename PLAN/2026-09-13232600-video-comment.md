# 视频评论 `_id` 幂等查重开发计划

## 1. 目标

为 `send_comment` 接口增加客户端 `_id` 幂等查重能力。

- 客户端传入 UUID v4（带分割符）作为 `_id`
- 若数据库中已存在相同 `_id`
  - 不允许重复插入
  - 返回 `code=5001`
  - 返回 `message=评论已经存在`
- Redis 作为幂等缓存，PG 作为最终事实源
- PG 命中后回填 Redis，避免重复查库

## 2. 方案选择

推荐把查重编排放在 **CASE 层**：

- API 层只负责解析参数和统一返回
- CASE 层负责业务流程编排：先查重，再落库
- PORT / ADAPTER 负责抽象和缓存策略
- REPOSITORY 负责最底层 PG 查重

## 3. 已确认现状

- `CommentCommand` 已包含 `_id: Option<String>`
- `gate_http` 的 `send_comment` 链路已经透传 `cmd`

- `port/src/cola_video/comment/check.rs` 已存在检查端口
- `repo_adapter/src/video/comment/check.rs` 已存在适配器壳子

## 4. 实施拆分

### 4.1 Port 层

文件：`D:\rust\short-video\port\src\cola_video\comment\check.rs`

新增 trait 方法：

- `exists_by_client_id(client_id: String) -> anyhow::Result<bool>`

职责：声明“按客户端幂等 ID 查重”的能力。

### 4.2 Adapter 层

文件：`D:\rust\short-video\repo_adapter\src\video\comment\check.rs`

实现 cache-aside：

1. 先查 Redis：`video:comment:dup:{_id}`
2. Redis 命中直接返回 `true`
3. Redis 未命中时查 PG
4. PG 命中后写入 Redis
5. PG 未命中返回 `false`

建议：

- 只缓存正例（已存在的 `_id`）
- TTL 先设为 7 天
- 缓存失败不影响主流程，只记录 warn

### 4.3 Repository 层

文件：`D:\rust\short-video\repository\src\video\pg\comment\check.rs`

新增方法：

- `exists_by_client_id(client_id: &str) -> Result<bool, sqlx::Error>`

SQL：

- `SELECT EXISTS(SELECT 1 FROM cola_video.comments WHERE _id = $1)`

建议同步确认数据库是否已有 `_id` 唯一索引；若没有，后续应补唯一约束作为最终兜底。

### 4.4 CASE 层

文件：`D:\rust\short-video\cola_video\src\case\comment\add.rs`

在调用 `send_comment(...)` 前：

1. 校验 `cmd._id` 存在
2. 调用 `ctx.video.comment.check.exists_by_client_id(...)`
3. 若命中，返回 `评论已经存在`
4. 若未命中，继续正常发布

### 4.5 API 层

文件：`D:\rust\short-video\cola_video\src\api\comment\add.rs`

统一错误映射：

- 如果 CASE 返回“评论已经存在”
  - 返回 `AppData::err(5001, "评论已经存在", None)`
- 其他错误保持原有失败返回

## 5. 验收标准

- 同一个 `_id` 重复请求不会重复插入
- 重复请求返回 `code=5001`
- 重复请求返回 `message=评论已经存在`
- Redis 命中时不会再查 PG
- PG 命中后会回填 Redis
- 代码符合当前项目分层与命名规范
